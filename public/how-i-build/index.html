How I build Tiny Data Adventures

personal data projects

Tiny Data Adventures take big, messy datasets (fossil records, museum catalogs, eruption reports, reef surveys) and make them accessible to everyone: easy to read for someone new to the data, and usable with a keyboard, a screen reader or without color.

I'm a product designer and a data enthusiast, not a data engineer. Claude Code gets me from a dataset to a working visualization fast; my eye and judgment decide what ships. Outside these solo projects, this is how I'd bring it to a team: running prototypes people can react to instead of static mocks, and small, well-scoped changes made directly in the codebase alongside engineers.

No Figma file, no design system up front. I designed these apps directly in code, because I wanted to see the data first. The system came out of the code afterwards, which is why so much of the work below is consistency and accessibility audits.

02 · Context, not prompts

Memory and know-how

A CLAUDE.md in each repo is its memory; skills are routines that travel between projects.

Memory needs maintenance too. Tracing Origins' CLAUDE.md grew to about 44,000 words, full of reversals, and all of it loads every session. Treat it like code: keep it short, archive the history, delete what's superseded.

The three skills I distilled from these projects:

visual-consistency-qa

Aligns radius, color roles, spacing and type, so they can become tokens.

wcag-audit-learning

"Learning" because I check every case by hand and talk each fix through before it's applied.

design-tokens-system

Fixes contrast and sizes in one place, and holds each project's visual identity.

Each project's tokens page shows what is tokenized and what isn't yet.

05 · Takeaways

What I've learned working this way

    Context over prompts

    I talk to Claude like a coworker. The CLAUDE.md and the skills carry the precision.

  2. 02

    Verify everything

    Learn the fixes
